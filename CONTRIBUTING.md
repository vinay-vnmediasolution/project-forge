# Contributing

Project Forge is currently a focused learning programme with one learner. Contributions are welcome when they improve clarity, correctness, practical value, or the quality of the learning experience without expanding active scope.

## Before proposing a change

1. Read the [project charter](PROJECT_CHARTER.md).
2. Check the active sprint and GitHub issues.
3. Use an existing issue or create a focused proposal before substantial work.
4. Keep speculative ideas in the parking lot until prioritised.

## Good contributions

- Correct an inaccurate explanation.
- Improve an exercise or acceptance criterion.
- Add a realistic, sanitised use case.
- Strengthen a test, architecture trade-off, or safety consideration.
- Make setup or learning evidence clearer.

## Not yet

- Websites and branding systems
- New channels or community infrastructure
- Large framework collections
- Unrelated tutorials
- Major project scaffolds without an approved issue

## Pull requests

Keep pull requests small and connected to one outcome.

Include:

- what changed and why;
- the issue or learning objective;
- how the change was checked;
- any trade-offs, limitations, or follow-up work.

Do not include:

- secrets or credentials;
- employer or client-confidential information;
- identifying production data;
- generated content that the contributor cannot explain.

## Documentation style

- Use plain language and concrete examples.
- Distinguish fact, recommendation, and personal reflection.
- Prefer a small diagram when it clarifies a relationship.
- Link to authoritative sources for claims likely to change.
- Avoid arbitrary tool lists; explain why a tool is relevant.

## Definition of done

Use the relevant definition in the [project charter](PROJECT_CHARTER.md#definition-of-done). Not every documentation change needs deployment, Docker, or a social post. Quality should be proportionate to the outcome.
